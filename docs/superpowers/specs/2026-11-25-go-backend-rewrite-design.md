# Go 后台重写设计

## 目标与约束

将现有 Java 后台全部重写为 Go，最终 Go 服务可独立替代 Java 服务；前端源代码及用户可见行为保持不变。以现有代码、配置、数据库结构、测试和运行行为为兼容依据；范围包括前端未直接调用但现有对外提供的接口和后台任务。既有数据必须能够安全升级和回滚。性能改善不是以牺牲现有功能或权限行为为代价的目标。

## 实施方案

可选方案一是一次性翻写后整体切换：最终架构简单，但缺乏持续的行为对照，差异集中暴露。方案二是在开发和验证期间保留 Java 基准，按业务链路逐步实现 Go，完成全部兼容验证后整体切换；选择方案二。并存仅用于开发及受控验证，最终运行不依赖 Java。每条链路应包括接口、鉴权、业务规则、数据操作、错误和边界行为，避免以接口数量替代功能完成度。

## 兼容边界

- 保持 HTTP 路径、方法、参数、状态码、响应结构、分页、错误语义、文件上传下载及静态资源行为；核对前端、桌面端和 MCP bridge 的调用。
- 保持认证、授权、密码、令牌及会话语义；尤其验证现有账号、已有令牌与权限规则。不得通过放宽权限实现兼容。
- 保持文档、知识库、搜索、评论、版本、分享、通知、附件、用户和系统管理等现有能力，以及 WebSocket 协作、AI 流式响应和 MCP 相关能力。
- 支持现有 PostgreSQL 数据、初始化和迁移历史，明确新库和存量库的启动路径；不修改或重写既有 Flyway 历史。存储、Redis、配置、定时清理和外部服务的行为需逐项核实。
- 兼容现有部署入口、配置和数据卷；如 Go 必须调整内部配置或构建流程，提供明确迁移方式，不要求用户修改前端。

## 执行与验证

1. 建立控制器、WebSocket、定时任务、数据库、外部集成和各客户端调用的清单，标记证据、缺口和验收状态。
2. 构建隔离测试环境和可重复的兼容测试，以 Java 为行为基准；对数据变更、权限、流式响应、并发和异常路径进行针对性验证。
3. 在 Go 中分业务链实现并逐项对照，包括部署、初始化、升级与恢复；迁移中保留 Java 以供对照，不对正式数据进行实验。
4. 全量功能、客户端、数据升级、构建和部署验证通过后切换默认后台；记录回滚方案。只有确认全部 Java 后台能力已替代，才移除 Java 运行依赖。

## 完成标准

现有前端无需修改即可通过核心及边界业务流程；接口和权限对照通过；已有数据库与文件可用，新安装和升级均通过验证；WebSocket、流式响应、后台任务和对外集成均有可复现验证；部署产物只需 Go 后台。任何无法确认的能力或未覆盖测试须明确列出，不能宣称全量兼容。

## 待实施阶段核实

完整接口清单、实际客户端调用、令牌跨实现兼容、数据库初始化与 Flyway 状态、Redis 的实际使用、文件存储及 MCP 传输细节，均需基于源码和隔离环境逐项确认。Go 框架和库由实现阶段依据现有行为、测试能力与维护成本选择。

审查补充：客户端还存在原生 fetch、axios 直接调用及令牌自动刷新；接口扫描不能只依赖统一请求封装。协作需验证 `/ws/doc/{docId}?token=...` 的握手、消息和断线行为；AI SSE 需验证帧格式和取消。部分业务、认证及校验错误通过 HTTP 200 和响应体代码表达，兼容测试必须同时检查 HTTP 与响应体。新库测试需覆盖初始管理员，存量库测试需核对初始化和 Flyway 历史，避免重复初始化。
